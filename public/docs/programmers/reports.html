Домен 07Отчёты и статистика

Единая универсальная система построения и исполнения отчётов (report engine) поверх таблиц RPT_*, с очередью задач и планировщиком. Диспетчеризация — не статический код, а метаданные: какой PL/SQL считает отчёт, хранится в таблице скриптов, а не в исходниках.

Для руководства
Что это простыми словами Внутренний инструмент, которым сотрудники строят отчёты компании — ежедневная статистика, финансовые сводки, маркетинговая аналитика по каналам привлечения.
Состояниев целом в порядке Работает стабильно, самый низкий по значимости риск среди всех восьми разделов системы. Единственная находка — в планировщике регулярных отчётов отключена обработка ошибок.
Главный риск для бизнеса Если запланированный отчёт (например, ежедневная статистика) перестанет строиться из-за ошибки — об этом сейчас никто не узнает: сбой проходит тихо, без уведомления ответственных. Риск — не в деньгах напрямую, а в том, что руководство может некоторое время принимать решения по отчётам, которые незаметно перестали обновляться.

Диспетчеризация "скрипт как данные"

Архитектурная особенность, не баг

REV_EXEC.OnTaskProcess(taskId) подгружает текст PL/SQL-скрипта из таблицы скриптов (REV_SCRIPT.getScript) и выполняет его через EXECUTE IMMEDIATE. Обычно это однострочный вызов конкретной процедуры вида BEGIN STAT_PKG.Daily_Statistics(:taskId); END;. То есть привязка "отчёт → код, который его считает" хранится как данные в БД и правится через административный интерфейс — при отладке нужно смотреть в саму БД, а не только в исходники схемы.

Второй слой — сборка файла результата: сырые данные (tab-delimited текст или recordset-BLOB) выгружаются на диск, внешний native-компонент (судя по именам процедур — Delphi-DLL/COM) делает mail-merge шаблона с данными и кладёт готовый файл обратно; Oracle только координирует через файловую систему, сам документы не рендерит.

REV_REPORT — ядро домена

REV_REPORT
таблицы: RPT_REPORT, RPT_TASK(_RESULT), RPT_SCHEDULER, RPT_PARMS, RPT_CATEGORY, RPT_OUTPUT

Разделы: карточки/списки отчётов (CRUD над RPT_REPORT), планировщик (расчёт следующей даты запуска по типу расписания — Daily/Weekly/Monthly/Once), задачи/исполнение (обёрнуто вокруг объектного типа Obj$Task — конструктор Obj$Task(taskId), методы .Cancel/.Save/.addToResult/.updateLog/.p(name), сам тип типа в дампе не встречается), категории и превью.

Отключённая обработка ошибок в планировщике

В job_operation и job_next_runtime блоки EXCEPTION WHEN OTHERS закомментированы целиком — любая ошибка при создании/обновлении задания сейчас падает необработанным исключением, а не откатывается с понятным статусом, как задумывалось изначально (видно по комментариям).

Незавершённая фича расписания

Ветка "N-й будний день месяца" обрамлена комментарием "ПОКА НЕ ОБРАБАТЫВАЕТСЯ — ЗАКРЫТ ДОСТУП ИНТЕРФЕЙСОМ!!!" и содержит отладочный RAISE_APPLICATION_ERROR, который взорвётся, если код когда-нибудь станет достижим.

Дублирующийся legacy-код

job_operationOLD, job_propertiesOLD, job_next_runtime_old — полные копии текущих процедур, не объявлены в спецификации, явный неудалённый legacy.

Отчёты-исполнители

STAT_PKG

Набор конкретных "репортов-как-код": Daily_Statistics, WeeklyIncoming, Monthly_Statistics, Marketing_Profit_Stat и др. Каждая процедура — самостоятельный ETL, читает параметры через Obj$Task.p(...), строит tab-delimited текст. Вызывается только через диспетчер (прямых статических вызовов в дампе нет).

ASMRGA (Marketing Research)

Цепочка зависимых отчётов: CREATE_PARENT_ALINE строит служебную таблицу истории статусов подписки, от неё зависят срезы активных студентов по категории/курсу с разбивкой по полу/возрасту/региону.

Мягкая зависимость между отчётами

Зависимые отчёты проверяют актуальность родительского прогона только предупреждением в лог, не блокируя выполнение — отчёт может тихо посчитаться по протухшим данным.

MS_PRINT / REV_MATREPORT

MS_PRINT.NS_LIST — список для печатной (не email) рассылки по дню рождения/долгу/активности. REV_MATREPORT — привязка вопросов анкеты к ячейкам Excel-шаблона, включая storage_create — динамическое (DDL на лету) пересоздание таблицы-пивота с колонкой на каждый вопрос анкеты.

Хрупкое кодирование через LIKE-маску

В обоих пакетах бизнес-семантика кодируется строковой конкатенацией без ELSE-ветки: CASE credit||debet WHEN '4070' THEN ... (без учёта новых кодов) и TO_CHAR(status||status_old) LIKE '6%' — хрупко к появлению новых кодов справочника.
