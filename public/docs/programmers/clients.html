Домен 01Клиенты и территории

Карточка клиента, географическая иерархия (для расчёта почтовых зон), преподаватели и их назначение на подписки, консультанты (внешние партнёры по продажам), и приём заказов с сайта до момента, когда заявка становится настоящим клиентом.

Для руководства
Что это простыми словами Единая карточка клиента, которую видит оператор: кто клиент, где живёт, кто его учит, кто его привёл (партнёр-консультант) и что он заказал на сайте.
Состояниетребует внимания Работает, но заявки с сайта сегодня всегда обрабатываются вручную операторами — готовая автоматика, которая могла бы сама превращать заявку в клиента и экономить время операторов, в коде есть, но выключена.
Главный риск для бизнеса Каждая веб-заявка — это ручной труд, хотя мог бы быть автоматический. Также найден полностью пустой модуль под клиентскую логику (заявлен, но никогда не реализован) — признак недоведённой до конца задачи из прошлого.

REV_PROFILE — карточка клиента

Центральный пакет UI оператора для ведения клиента: общие данные, подписки/посылки, корзина, денежные операции, возвраты, звонки, льготы, контракты — по сути весь "экран клиента" в одном пакете (~46 процедур).

REV_PROFILE
таблицы: CLIENT, CLIENT_PROPERTY, WEB_CLIENT, CLIENT_BASKET, CLIENT_SUB, CONTAINER, MONEY_DIST, MONEY_SOURCE, BENEFIT, ESCC_TYPE/ITEM/CODE и ещё >20
ПроцедураЧто делает
general_frameГлавный фрейм карточки клиента (вкладки: продукты, контакты, распределения, платежи, возвраты, кампании, ДЗ, консультант, веб)
client_propertiesЗагрузка/создание профиля, привязка веб-заявки (web_client) к client_id
client_search / client_search_listПоиск клиента, включая поиск по кодам старой системы ЕШКО (escc_type/item/code)
client_updateСоздание/обновление клиента, проверка дублей-"близнецов" (twins_code)
basket_listИерархический (CONNECT BY) список позиций корзины клиента
container_updateСоздание/обновление посылки, пересчёт льгот при смене состава
subscription_updateОбновление подписки на курс, расчёт долга/доступности блоков
distribution_list / payment_listСписок денежных распределений и платежей клиента
Мёртвый код / дубли

client_update и call_update почти дословно дублируют друг друга (сохранение клиента + проверка twins_code). Вкладки "Домашние задания" и "Консультант" физически подгружаются через iframe из REV_TEACHERS/REV_CONSULTANT, а не прямым PL/SQL-вызовом — межпакетная связь идёт через встроенные URL, а не API.

Легаси-миграция в проде

Поиск клиента через escc_type/escc_item/escc_code с явным комментарием "типы баз в старой системе ЕШКО" — следы миграции с предыдущей системы, оставленные и работающие в текущем проде.

REV_CONTACT — журнал контактов

REV_CONTACT
таблицы: CLIENT_EVENT(_LOG), SYSTEM_BLOB, SUBJECT, BENEFIT, SMS, GMS_MESSAGE, RPT_REPORT

Журнал звонков и событий (client_event), рассылка писем/боксов писем, стандартные ответы, SMS-переписка — весь "разговор" с клиентом в одном месте. contact_action — самая насыщенная процедура: смена стоимости подписки, добавление/удаление данных студента, отправка "rest"-писем с разными скидками (0/10/15% — коды S025.01/02/05 зашиты через REV_CONST).

Мёртвый код

В теле пакета лежат 4 полностью закомментированные старые процедуры (answer1_old и др.) — не удалены, просто не вызываются.

rev_territory_tree_v02 — география

rev_territory_tree_v02
таблицы: AREA_TREE, AREA_TYPE, ZIPCODE_ZONE, USER_LIST

Web-пакет (mod_plsql) для дерева территорий: чтение для UI, поиск по названию (CONNECT BY + stragg), "хлебные крошки" от корня до узла, CRUD узлов, привязанных к почтовым зонам.

Дублирование

get_territory и get_territory_HTTP — практически дословные копии друг друга.

Правило в тексте ошибки, не в коде

Узел территории физически нельзя удалить, если на него ссылаются адреса клиентов — но это выражено только текстом сообщения об ошибке в WHEN OTHERS, а не явной проверкой в коде.

REV_TEACHERS — преподаватели

REV_TEACHERS
таблицы: teacher, teacher_name, teacher_status, homework, client_sub, category, obj$teacher

Учёт карточек преподавателей, назначение/переназначение на подписки учеников, приём и оценка домашних заданий, обмен XML с клиентским JS-интерфейсом.

ПроцедураЧто делает
TeacherChangeПереназначение преподавателя на активные подписки/ДЗ с учётом статусов курса
GetClientItemsВыборка присланных учеником работ/уроков по категориям для интерфейса преподавателя (~320 строк)
SaveHomeWorkСохранение/оценка/удаление ДЗ по XML от клиента
GetTeacherAlternativeПодбор свободных альтернативных преподавателей на курсе
Заглушка вместо логики

teachersOperations — тело добавления/правки преподавателя полностью закомментировано, реально выполняется только пустой COMMIT и возврат "ok". Не входит даже в публичную спецификацию пакета.

Хак кодировки

Повторяющийся приём "избавляемся от бага перекодировок на лету": utl_url.unescape(utl_url.ESCAPE(..., 'WINDOWS-1251'), 'UTF-8') — двойное перекодирование как обход бага получения XML-параметров.

REV_CONSULTANT — внешние партнёры

REV_CONSULTANT
таблицы: CLIENT_CONTRACT(_TYPE/_STATUS), CHANNEL, CLIENT_PAYROLL, CLIENT_BASKET, CLIENT_SUB, CATALOGUE

"Консультант" — это не сотрудник, а внешний реферальный партнёр по продажам курсов, технически представленный обычной записью CLIENT с договором (CLIENT_CONTRACT) и привязанным маркетинговым каналом (CHANNEL) для отслеживания приведённых им клиентов. Пакет считает и фиксирует комиссионные выплаты (CLIENT_PAYROLL) по проданным курсам.

Скрытый побочный эффект

contract_update при первом сохранении договора неявно создаёт два канала (Provider, затем Issue) с автогенерируемым кодом 'C_' || channel_id — критичная бизнес-логика, спрятанная внутри обычной update-процедуры.

Кэш без инвалидации

Пакетная переменная dddwContractStatus кэширует справочник статусов один раз на сессию — если справочник изменится, кэш не обновится до переподключения.

WORDERS / WEB_ORDER — заявки с сайта

WORDERS · WEB_ORDER · REV_API.worder_registration
таблицы: WORDERS_MAIN/ADDRESSES/SETTINGS/ERRORS, WEB_CLIENT, WEB_BASKET, WEB_ORDER_AUTO_REG

Реальная точка входа — REV_API.worder_registration: сайт шлёт сырую строку wid=...;wtype=...;email=..., парсится самописным парсером, проверяется на спам, сохраняется в WORDERS_*, затем копируется в очередь оператора (WEB_CLIENT/WEB_BASKET) через WORDERS.InitializationOneOrder — заказ ждёт ручной обработки оператором.

Автоматизация есть, но выключена

WEB_ORDER.AUTO_REG — полностью реализованное автосопоставление заказа с существующим клиентом (по email/телефону) или создание нового — но вызов этой процедуры закомментирован в worder_registration, переменная жёстко инициализирована в 0. Все веб-заказы сегодня идут только через ручную очередь.

Точечная блокировка в бизнес-коде

Хардкод конкретного IP 217.112.35.81 прямо в проверке спама — единственная защита публичного эндпоинта, кроме словаря спам-слов. Нет проверки токена/подписи запроса вообще.

Мелкие пакеты домена

ESCC_USER

Одна процедура USER_DATA(vUSER_ID, ...) — параметр vUSER_ID полностью игнорируется, запрос жёстко фильтрует WHERE ul.USER_ID = 323. баг/заглушка

ACT_CHANNEL

Одна функция CHANNEL_CLONE — клонирует маркетинговый канал под новым кодом. USER_ID нового канала жёстко = 200 (тот же паттерн "системного пользователя", что и 323 в ESCC_USER). COMMIT в процедуре отсутствует.

POST_JOB

Отчётность по батчам почтовой рассылки. баг маппинга — в CASE-расшифровке упаковки дублируется WHEN 8, второе значение ("Электронная почта") никогда не сработает.

ESCC_CLIENT

Полностью пустой пакет-заглушка — и спецификация, и тело объявлены, но не содержат ни одной процедуры. Несмотря на говорящее имя, реализация так и не была написана (или была удалена). пустышка

CM_AC

Автоматическая кампания взыскания долга (email-напоминания должникам) — одна из трёх параллельных реализаций этой задачи в схеме. Полный разбор — на странице маркетинг-кампаний.
