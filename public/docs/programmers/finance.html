Домен 02Финансы и платежи

Полный цикл денег курсов дистанционного обучения: приём оплат тремя разными каналами (почтовый перевод, банк, ЕРИП), автоматическая и ручная разноска на счета клиентов, списание при возврате или порче материалов — и всё это через единый бухгалтерский журнал MONEY_DIST.

Для руководства
Что это простыми словами Всё, что касается денег клиента: получили оплату — списали долг; вернули товар или он потерялся — списали часть долга обратно. Отдельно — обмен данными с ЕРИП (национальная система приёма платежей).
Состояниетребует внимания Основной учёт работает. Автоматическое сопоставление оплаты с клиентом — эвристика "совпала фамилия и ровно совпала сумма"; если не совпало — платёж зависает и ждёт, пока сотрудник разберётся вручную.
Главный риск для бизнеса Пароль к ЕРИП хранится открытым текстом прямо в коде базы данных — это доступ к каналу приёма платежей всей компании, и он виден каждому, у кого есть доступ на чтение исходников. Кроме того, половина автоматизации обмена с ЕРИП не доделана (заглушки вместо кода) — реальная сумма к оплате туда не передаётся, судя по всему, ЕРИП узнаёт её другим путём. Рекомендация: сменить пароль и вынести секреты из исходников в первую очередь.

Модель данных

Долг клиента считается по бухгалтерскому журналу MONEY_DIST — двойная запись дебет/кредит по номерам счетов из MONEY_ACCOUNT:

Код счётаНазвание
10World (внешний мир — деньги клиента)
15Transit (деньги неопознанного плательщика)
40Invoice (выставленный счёт)
50Return (возврат)
60Loss (потеря/порча материалов)
70Material (материалы)

Функция UK_Client_Debt(clientID) — официальный расчёт долга — декодирует пару credit||debet: '4070'=выставление счёта, '1040'=оплата посылки, '4010'=потеря материалов, '1015'/'1510'=деньги на курс/клиента, '5040'/'4050'=возврат, '6040'/'4060'=компенсация потери. Именно эту расшифровку мы использовали при построении собственного view API_CLIENT_FINANCE_HISTORY для кабинета.

Объектные типы — восстановлено по вызовам

Важная оговорка

Типы OBJ$CLIENT, OBJ$BOX, OBJ$MONEYDIST используются в десятках пакетов, но их собственные тела не попали в дамп схемы (не экспортированы). Интерфейс ниже восстановлен по местам вызова — реальная формула внутри методов недоступна напрямую, перепроверяйте перед использованием в проде.

OBJ$BASKETITEM.DebtSumДолг по курсу целиком
Obj$MoneyDist(clientId).makeTrans(...)Универсальная точка создания проводки в MONEY_DIST
Obj$MoneyDist.getBalance(Acc, Obj, ...)Баланс по счёту/объекту за период

Самый большой и центральный пакет домена.

Логика не там, где ожидаешь

Реальная проводка возврата (счета 40↔50) выполняется здесь, а не в REV_MDERETURNS — домен "возвраты" разорван между профильным и фактическим пакетом.

Ошибки глушатся

AutoDistribution оборачивает вставку в EXCEPTION WHEN OTHERS THEN ROLLBACK без логирования — платёж просто останется неразнесённым без диагностики.

Известный техдолг, признанный в коде

Комментарии прямо в спецификации: -- Remove these procedures from this packages -- и -- Remove these modules from this packages -- — процедуры, которые давно должны были переехать в другой пакет.

REV_MDERETURNS — регистрация возвратов

REV_MDERETURNS
таблицы: RETURN_SHIPMENT, RETURN_ITEM, RETURN_CLOSE_MONTH, CRUTCH_RETURN_POSTCODE

Логистика возврата ("стол находок" для вернувшихся посылок): регистрация по коду клиента/накладной/штрихкоду, блокировка закрытых дней/месяцев для новых возвратов, построение формы утверждения по позициям. Сам не пишет в MONEY_DIST — только фиксирует факт возврата, деньги проводит REV_MDEPAYMENTS.

Костыль в названии таблицы

CRUTCH_RETURN_POSTCODE — буквально "костыль", временный обходной путь сопоставления 13-значного штрихкода посылки с CONTAINER_ID.

REV_LOSS — списание порчи материалов

REV_LOSS
таблицы: MONEY_LOSS, MONEY_LOSS_TYPE, CLIENT

Единственная точка входа save_loss (add/del/cor): add — дебет Invoice(40)/кредит Loss(60), del — сторно, cor — корректировка суммы. В отличие от AutoDistribution, всё идёт через obj$moneydist(...).makeTrans(...) — это более аккуратный, "новый стиль" кода того же назначения.

ERIP — интеграция с белорусской системой расчётов

ERIP
таблицы: ERIP_SETS_CLIENTS, ERIP_SET_INFO, ERIP_TRANSFER_LOG

Модель — файлово-пакетная через FTP (ftp.hgrosh.by, внешний агрегатор), не онлайн-API: выгрузка справочника клиентов в CSV, импорт ответных файлов с FTP. Фактический парсинг входящих ЕРИП-платежей выполняет не этот пакет, а REV_MDEPAYMENTS.LoadPayment (читает из того же каталога).

Пароль в открытом виде в исходнике

FTP-логин/пароль (eftp_user/eftp_pass) заданы константами прямо в спецификации пакета — виден любому с доступом на чтение ALL_SOURCE.

Половина процедур — пустышки

erip_upload, erip_ftp_export, erip_download, erip_import — тела BEGIN NULL; END;. Выгрузка клиентов никогда не заполняет реальную сумму к оплате (SUMMA/FINE всегда 0) — судя по всему, ЕРИП узнаёт долг не из выгрузки, а онлайн через API_SERVICE_ACCOUNT.ACCOUNT_CLIENT_TOTAL_DEB (см. API-слой).

Прочие пакеты домена

API_SERVICE_ACCOUNT

13 строк: ACCOUNT_CLIENT_TOTAL_DEB(CLIENT_ID) просто вызывает OBJ$CLIENT(CLIENT_ID).GETTOTALDEBT. Судя по соседству в файле с ACTION_PAY/партнёрской отчётностью — фасад для внешнего запроса актуального долга в реальном времени (в т.ч. вероятно, ЕРИП).

ACTION_PAY

Ложный след по имени — не про оплаты клиентов, а интеграция с партнёрскими CPA-сетями ActionPay/Admitad (плата за лиды вебмастерам): проверка уникальности лида, сверочные отчёты.

MONEYDIST_PKG_UTILS

Две чистые SQL-функции getBalance/getBalanceAcc — тот же расчёт баланса, что делает OBJ$MONEYDIST.getBalance, только без создания объекта. Похоже на "запасной путь".

MD_PKG_UTILS / MD_PKG

Тоже во многом ложный след — несмотря на имя "MONEYDIST", это в основном маркетинг/CRM-автоматизация (рассылки, дни рождения, бонусы операторам, детекция фейковых заказов). К долгу относится только UPDATE_DEBTORS (пересчёт кэша MONEY_DEBT_CLIENTS: формула DebtSum = ReceivedSum + ReturnedSum + LostSum − InvoicedSum) и GET_LIST_DEBTORS (CSV-отчёт "должники"). CONFIRM_SHIPMENT/CONFIRM_RETURN строят официальный бухгалтерский "Реестр оказанных услуг" — похоже на регуляторную/налоговую отчётность.

DENOMINATION

DN10K(sm) = sm/10000 — конвертация исторических сумм в "старых рублях" (до деноминации Беларуси 2016 года) для вывода в отчётах.

RECALCULATION

KNOWLEDGE_DAY_ADDING — одноразовый промо-хак с жёстко зашитым диапазоном дат 01.08.2020–04.10.2020 и конкретными ID акции/товара. гарантированно мёртвый код

Жизненный цикл долга клиента

От выставления счёта до погашения — с двумя опциональными ветками (возврат, списание) и ежедневным пересчётом кэша должников, на котором строятся SMS-напоминания.
См. также: CM_AC / CAMPAIGN_ACCOUNT / CM_DEB — три параллельные реализации автоматической кампании взыскания долга.
