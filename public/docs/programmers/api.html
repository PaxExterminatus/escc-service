Домен 08 · ключевой разделAPI-слой интеграций

Под общим ярлыком "API" в схеме скрываются пять независимых, не связанных друг с другом интеграций разного возраста: call-центр (Oktell), мессенджинг (Viber через Hyber), две разные учебные LMS (eFront и Campus), и публичный сайт. Слой чистых READ-ONLY view API_*, на котором построен наш Laravel-сервис — самый новый и самый чистый способ; всё описанное ниже — гораздо более старые и "грязные" способы того же самого.

Для руководства
Что это простыми словами Все "двери", через которые внешние системы обращаются в эту базу данных: наш собственный личный кабинет, две разные платформы онлайн-обучения, телефония call-центра, сервис Viber-рассылок.
Состояниетребует срочного внимания Это раздел с самой высокой концентрацией рисков безопасности во всей системе. Пять "дверей" построены в разное время, без единого стандарта защиты — у нескольких из них нет вообще никакой проверки того, кто стучится.
Главный риск для бизнеса Найдено: отключённая проверка кода доступа к курсу; тестовые учётные записи с бессрочным доступом, оставленные в боевой системе; один и тот же предсказуемый пароль, выдаваемый абсолютно всем клиентам при синхронизации с внешней платформой обучения; публичная точка приёма заявок с сайта вообще без проверки подлинности запроса (кроме одного заблокированного IP-адреса). Если планируется расширять интеграции или открывать систему более широкому кругу партнёров — начинать нужно именно с ревизии этого раздела.

Часть кода использует парольную конвенцию Revelation rev_util.parm (пары массивов имя/значение) для собственного AJAX-слоя внутренней CRM-панели — это внутренний UI-механизм, не внешний API. В дампе нет GRANT/CREATE SYNONYM — кто именно физически имеет право звать эти процедуры снаружи, по одному дампу не восстановить.

APISAS_EFRONT — интеграция с eFront (детально)

APISAS_EFRONT
таблицы: API_EFRONT_DATA, CLIENT_SUB_ONLINE_ACCESS(_ERROR/_LOG)

Единственное место в дампе, где что-либо пишет в API_EFRONT_DATA. Ни одного UTL_HTTP-вызова наружу в пакете нет — направление вызова eFront → Revelation (LMS сама вызывает хранимую процедуру через JDBC/OCI-мост, минуя HTTP).

Точка входа: EFONLINE(cl_code, rq_type, rq_code, node_id, lesson_item) — простые скаляры, без какой-либо проверки авторизации внутри процедуры.

Механизм — "почтовый ящик" в таблице (PK по CLIENT_ID, одна строка на клиента, история не хранится): старый ответ удаляется, считается новый XML по rq_type (data=список курсов, code=проверка доступа, reset=сброс), конвертируется в BLOB и одним INSERT кладётся обратно. Даже фатальная ошибка результируется строкой в этой же таблице (код ошибки 6 + трейс), а не пробрасывается наружу.

Важно для интеграции с нашим Laravel

API_EFRONT_DATA — не пассивный кэш, а результат последнего запроса. Строка появляется/обновляется только когда eFront реально вызвал EFONLINE для этого клиента — нет фонового обновления/TTL. Для клиента, который давно не заходил в eFront, строки может не быть вовсе, либо она устаревшая.

Отключена проверка кода доступа к курсу

В getonlineaccesscourse: IF TRUE THEN --access-px [online_acc_code = acc_code] — любой код доступа к курсу принимается как верный. Для урока проверка (getonlineaccesslesson) осталась настоящей.

Тестовые ID клиентов с вечным доступом в проде

2333 и 21673 зашиты как "тестовые клиенты" — получают доступ на 200 лет вместо обычных 3 (get_test_client). Отдельно — APISAS.RESET_CODE буквально делает UPDATE ... WHERE CLIENT_ID = 2333 вне зависимости от переданного параметра.

get_homework ничего не сохраняет

Валидирует пришедшее от eFront домашнее задание и... ничего не пишет — реальный INSERT закомментирован, возвращается просто "1"/"0".

Логирование вызовов отключено

Таблица APISAS_LOG создана, но ни один пакет в неё не пишет. Единственный след — закомментированный вызов --APISAS.LOG_ADD(...) — раньше у APISAS была процедура логирования, сейчас в пакете осталась только RESET_CODE.

REV_API_GMS · REV_API_TOOLS

Комментарий не поспевает за реальностью

REV_API_TOOLS.API_authBasicHTTPS подписан комментарием "отправка запросов API esputnik", но единственный текущий вызывающий шлёт запросы в Viber/Hyber — след смены SMS/Viber-провайдера без актуализации документации в коде.

APISAS_CAMPUS — вторая учебная платформа

APISAS_CAMPUS

Отдельная от eFront внешняя учебная платформа "Campus". USER_UPDATE_CALL — Revelation сам дёргает наружу (UTL_HTTP GET на жёстко зашитый внутренний IP 10.20.36.107:8080); USER_UPDATE_GETDATA/LIST_COURSE_LESSON — отдают курсор/XML для вытягивания кампусом (двусторонняя интеграция: push уведомлением, pull через REF CURSOR).

Единый предсказуемый пароль для всех аккаунтов

USER_UPDATE_GETDATA возвращает буквально константу '80295553238' AS PASSWORD для каждого синхронизируемого клиента — общий, предсказуемый секрет для инициализации учётки во внешней системе.

REV_API — приём веб-заявок с сайта

Полный разбор цепочки "заявка → клиент" — на странице Клиенты и территории. Здесь — только выводы, важные с точки зрения API-контракта.

Нет проверки авторизации/подписи запроса вообще

Ни EFONLINE, ни worder_registration, ни процедуры APISAS_CAMPUS не проверяют ни токен, ни подпись, ни даже Basic-Auth со стороны вызывающего. Единственная "защита" публичного веб-эндпоинта — один захардкоженный заблокированный IP и словарь спам-слов.

Но хотя бы не SQL-инъекция

Самописный парсер параметров (subGetValueFromName, ручной INSTR/SUBSTR вместо query-string/JSON) хрупок к спецсимволам в значениях, но результат идёт в bind-переменные, а не в динамический SQL — EXECUTE IMMEDIATE с конкатенацией пользовательского ввода в проверенных пакетах API-слоя не встретился.

Типичный вызов снаружи — два паттерна

Паттерн A (eFront) — простейший и без авторизации. Паттерн B (Viber) — единственный в этом домене с настоящей HTTPS Basic-Auth и обратным вебхуком.
