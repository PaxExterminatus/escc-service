Домен 04Заказы, склад и почтовая рассылка

Конвейер "от корзины клиента до физической (или электронной) отправки материалов курса": расчёт почтового тарифа, сборка посылки-контейнера, фиксация отправки с проводкой в бухгалтерию.

Для руководства
Что это простыми словами Как заказ клиента превращается в реально отправленную посылку: считаем стоимость доставки, собираем посылку, отправляем, отмечаем как оплаченную.
Состояниетребует внимания Работает, но ставка налога на почтовые тарифы задана в коде дважды, в двух разных местах, с двумя разными значениями — нет единого источника истины.
Главный риск для бизнеса Риск тихой финансовой неточности: если ставку когда-то поменяют в одном месте и забудут про второе, часть тарифов будет считаться неверно, и никто не заметит, пока не начнут разбираться жалобы клиентов или расхождения в отчётах. Также найден отчётный скрипт с захардкоженным ID одного конкретного клиента — признак разового решения, оставленного в общем инструменте.
Не всё, что называется похоже — про логистику

Часть пакетов из этого домена (REV_MARKET, WH) вопреки названиям относится к соседним, но иным поддоменам: REV_MARKET — рекламная логистика (промо-материалы по почтовым отделениям), WH ("data WareHouse") — ETL для маркетинговой сегментации клиентов, а не складской учёт. REV_GENERAL/REV_GENERAL_BS — вообще общий UI-фреймворк админки, не логистика. Не путайте при навигации по коду.

BOX_PKG_UTILS — точка отправки

BOX_PKG_UTILS
таблицы: CONTAINER, CLIENT_BASKET, CLIENT_SUB, CONTAINER_DEBT, OBJECT_CONTRACT, MONEY_DIST

Ядро "точки отправки" контейнера. BOX_SENDDATE(containerID) — главная процедура: переводит CONTAINER.STATUS_ID в boxStatusSent(70), ставит SEND_DATE, при CONTAINER_COST>0 создаёт бухгалтерскую проводку через Obj$MoneyDist, закрывает CONTAINER_DEBT, чистит "хвосты" по позициям корзины. Дополнительно — побочные эффекты на статус подписки (при "полном комплекте" или последнем блоке помесячного курса переводит CLIENT_SUB в завершённое состояние).

ФункцияЧто делает
BOX_CHECK_CATEGORYЕсть ли в контейнере товар заданной категории
BoxLastPaymentDateДата последнего успешного платежа по контейнеру
Магический префикс категории

Код "последнего юнита" курса строится как строка '18.' || LTRIM(...) — префикс 18. зашит в PL/SQL для сопоставления с CATEGORY.CATEGORY_CODE, привязка к структуре кода категорий нигде явно не документирована.

WEB_ORDER — автосоздание клиента из веб-заказа

WEB_ORDER
таблицы: WORDERS_MAIN, CLIENT, CLIENT_PROPERTY, WEB_ORDER_AUTO_REG(_ERROR)

AUTO_REG(WID) сопоставляет клиента по email/телефону: уникальное совпадение по телефону → дозаполняет email; уникальное по email → дозаполняет телефон; оба совпали на одном клиенте → выбор его; совпадений нет → AUTO_REG_CLIENT_CREATE. После определения клиента контейнер создаётся сразу со статусом Sent(70), почтовой схемой "email"(11) — весь конвейер сборки/тарифа обходится, посылка считается отправленной в момент создания.

Неоднозначные случаи не обрабатываются

Если email матчит нескольких клиентов — ветки в CASE нет, CLIENT_ID остаётся NULL, ошибка ловится только общим WHEN OTHERS и логируется в WEB_ORDER_AUTO_ERROR. Подробный разбор всей цепочки заявка→клиент — на странице Клиенты.

POST_FEE_PKG / POSTAL_RATE_CONTROL — почтовые тарифы

POST_FEE_PKG
таблица: POST_FEE

POST_FEE(post_schema, weight, cost, ...) маппит схему доставки на код тарифа и одну из двух моделей веса. Итог умножается на захардкоженный коэффициент 1.2 (НДС/наценка не из справочника).

POSTAL_RATE_CONTROL

GET_COST(code, addNds=1) — читает тариф, опционально добавляет НДС через отдельно захардкоженную константу NDS := 0.2.

Два независимых источника ставки НДС

POST_FEE_PKG использует множитель 1.2 прямо в формуле, POSTAL_RATE_CONTROL — отдельную константу 0.2. Единой точки истины по ставке налога для почтовых тарифов нет — при изменении ставки нужно помнить про оба места.

Прочие пакеты

WH

Вопреки названию — не склад. Единственная процедура CLIENT_CATEGOTY_CREATE (опечатка в имени) перестраивает таблицу-витрину WH_CLIENT_CATEGORY (TRUNCATE + INSERT) для маркетинговой сегментации по интересам; список категорий (Красота и здоровье, Программирование и т.д.) зашит ID прямо в SQL.

REV_MARKET

Не про заказы учеников — рекламная логистика: управление точками распространения листовок (почтовые отделения с остатками рекламных материалов). Есть редкая точка интеграции с внешней БД через database link market_p@stock (файл MARKET_P.DBF — легаси-система учёта остатков).

ADV_OBJECT_FINANCE / ADVOBJ_FININF

Два практически дублирующих друг друга генератора HTML-выписки по клиенту (курсы, оплаты, возвраты, остаток долга) в EMT3_CLIENT_MESSAGE.

Захардкоженный клиент в проде

ADV_OBJECT_FINANCE.FIN_CREATE(vCLIENT_ID) — параметр игнорируется, фильтр жёстко AND cs.CLIENT_ID = 2333. Похоже на одноразовый скрипт для конкретного клиента, оставленный в проде под видом параметризованной процедуры. ADVOBJ_FININF — корректно параметризованная, более поздняя версия того же самого — оба сосуществуют.

REV_GENERAL / REV_GENERAL_BS

Общий UI-фреймворк админки (HTML-обвязка, верхнее меню, права доступа, логирование действий) — включён в этот домен по заданию, но прямого отношения к логистике не имеет. Реальная логика сборки партии/возврата посылок физически находится в REV_PROCESSING и REV_WEB (не разбирались отдельно).

Жизненный цикл контейнера (заказа)

Пунктирный блок слева — альтернативный (и сейчас неактивный) путь: автосозданный веб-заказ проходит все шаги мгновенно, минуя тариф и сборку.
