Домен 06Маркетинговые кампании и сегментация

Самый большой по числу пакетов домен (24) — и не единая подсистема, а наслоение минимум четырёх поколений самодельных email/SMS-рассылочных движков, написанных в разное время поверх одной и той же core-модели. Старые версии не удалены — часть продолжает исполняться, часть осталась только как мёртвый код.

Для руководства
Что это простыми словами Автоматические маркетинговые рассылки: отбираем группу клиентов по признаку (не студент, скоро день рождения, есть долг) и рассылаем им письма/SMS по расписанию.
Состояниетребует внимания Функция работает, но реализована четыре раза за разные годы, и старые версии никто не убрал. Например, кампания "напоминание о долге" сегодня существует в трёх параллельных версиях одновременно, одна из которых заброшена.
Главный риск для бизнеса Это годы повторно потраченной работы разработчиков на одну и ту же задачу, и сейчас очень легко случайно сломать "не ту" версию кампании при изменениях, потому что непонятно, какая из нескольких версий действительно активна. Прежде чем инвестировать в доработку рассылок — стоит сначала навести порядок и оставить одну работающую версию каждой кампании.

Четыре поколения одной задачи

Общий принцип везде один: отобрать сегмент клиентов SQL-запросом → создать "рекламный товар" в каталоге → отгрузить его клиенту через obj$box.addProduct с почтовой схемой "email"(11) — система доставки писем переиспользует складскую/товарную подсистему: письмо технически является отгруженным контейнером с товаром.

ПоколениеПакетыХарактер
1. EM_*EM_MANAGER, EM_MANAGER_CAMP, DATA_MARKETINGТегирование клиентов десятками узкоспециализированных SQL-скриптов, синхронизация во внешнюю "Cross DB" по HTTP
2. EMT*EMT, EMT3, EMT4, EMTC, EMT_GENERAL, EMT_STATS, EMT_PP, EMT_ESCC_EMAILINGБолее развитый список-билдер с таблицей плана; часть синхронизируется через Heterogeneous Services database link @EMS
3. CM_*CM_DEB, CM_HF, CM_ETL, CM_ETLV3Stateful-движок поверх CLIENT_CAMPAIGN с именованными шагами и таймерами
4. CAMPAIGN_*CAMPAIGN_REMAIL, CAMPAIGN_ACCOUNT, CAMPAIGN_ALLОркестрация запуска/эскалации кампаний поколения 3, включая живой движок взыскания долга

EMS_* (EMS_SYNC, EMS_DATA, EMS_BASE_CLIENT, EMS_UTILITY) — отдельный, более поздний слой ETL выгрузки клиентской базы и статистики кампаний во внешний ESP (метрики CAMP_OPENS, CAMP_BOUNCES, CAMP_UNSUBSCRIBES — классика email-платформ типа MailChimp).

Три способа внешней синхронизации в одной схеме

(1) Heterogeneous DB link @EMS + DBMS_HS_PASSTHROUGH с ручным bind по одному ряду (EMT3) — тяжеловесно и медленно. (2) HTTP GET на internal middleware revapp/dbsync* без проверки полезной нагрузки, только по status_code (EM_MANAGER, CM_ETL, CM_DEB) — реальные данные читаются отдельным процессом на той стороне. (3) Явные ETL-таблицы EMS_DATA* + esccapp/ems/load (EMS_DATA) — самый структурированный и, похоже, самый новый способ.

Взыскание долга — три параллельные реализации

CM_AC · CAMPAIGN_ACCOUNT.DEBT_MANAGER · CM_DEB

Кампания взыскания долга (CLIENT_CAMPAIGN.TYPE_ID=11, "EDeb") реализована трижды:

ПакетСтатус
CM_ACЖивой. Оркестратор AC_DEB_RUN_REV: GSV.GSV_ACCOUNT → старт кампании → завершение погасивших → продвижение по шагам → синхронизация с внешней EMS по HTTP
CAMPAIGN_ACCOUNT.DEBT_MANAGERЖивой, но делегирует расчёт даты следующего шага в тот же CM_AC — то есть это надстройка, не альтернатива
CM_DEBзаброшен Весь функционал, кроме двух тривиальных функций, закомментирован — рабочей осталась только AC_MOVE
Магические числа вместо конфигурации

В CM_AC бизнес-константы зашиты в функции V() прямо в коде: DELAY=30 дней, MINDEBT=-3, ITERATION_PRODUCT=конкретный ID товара. Ссылка на dev-хост http://dev.office.eshko.net:8080/revapp/dbsync_deb — прямо в проде.

Хардкод тестового клиента в живом коде

CM_DEB.CHOICE_DAY содержит WHERE ms.CLIENT_ID = 2333 --VAL — закомментированный маркер разработчика, оставленный прямо в SQL-запросе.

Ключевые пакеты (детально)

CM_ETL / CM_ETLV3

Обе версии управляют одной и той же кампанией (TYPE_ID=7, "RemailelTL"), но с несовместимыми множествами имён шагов (RC/G2TM1/G2TM2 против ETL3FOTM2/ETL3ROTM2) — явно "v2" и "v3" одного движка, сосуществующие в БД одновременно.

EM_MANAGER_CAMP

Самый большой пакет домена (~3000 строк) — библиотека из ~25 узкоспециализированных процедур-скриптов (должники, "не студенты" до/после даты, активные студенты), каждая заканчивается тем же 15-строчным блоком отгрузки контейнера. Много копипасты.

Мёртвая процедура

EMDEB_ADDPRODUCT — рабочий INSERT/LOOP полностью закомментирован, тело реально исполняет только NULL.

EMT3

Крупнейший "рабочий" пакет старого поколения (~840 строк): синхронизация с внешней БД через DB-link @EMS, разметка каждого клиента одним SEND_TYPE (100-430: активный студент/выпускник/ отказник/давность заказа).

EMT_GENERAL.PLAN_EXECUTE

пустая заглушка Вызывает проверочную функцию, но реального действия не выполняет — похоже на недописанный обобщённый рефакторинг EMT.RUNNER_LIST.

EMT_ESCC_EMAILING

Строит общий бюллетень (ESCC_EMAILING): активные клиенты с email, минус заблокированные/ именинники/должники.

Копипаста при доработке

EMT_LOAD_EMAILING и escc_emailing — почти буквально одинаковый 400-строчный SQL продублирован дважды с минорными отличиями, вместо вынесения общей логики.
